# Regenerable embroidery

A textile decoration can now keep digitizing settings alongside its editable source artwork. Open **Digitize embroidery…** from a patch's Textile inspector. Choose source layers, ordered regions, threads, method, physical dimensions, and hoop clearance; rebuild the actual needle preview, scrub its command playback, then save. Solid paths are stitches, dashed paths are travel with the needle up, and orange marks request trims. Configured 3D decorations display those actual needle paths over their fabric base; the dedicated Embroidery window adds travel/trim inspection and playback. See [physical stitch surfaces and process settings](embroidery-process.md).

Basic settings are schema 25; opt-in underlay and process settings use schema 28. Each region references source artwork UUIDs rather than replacing shapes or words with generated points. Editing the vector, typography, linked source, or physical face size changes the regenerated program and its SHA-256 source digest. Preview generation is explicit and cached while settings are edited; every export regenerates from the current saved artwork. Save, native controls, MCP updates, and Undo use the same operation.

## Digitizing methods

- **Running:** follows open or closed vector contours, preserving flattened curve vertices and dividing long segments to the chosen maximum stitch length. Curves flatten with a maximum 0.05 mm control-to-chord error before 0.1 mm needle quantization.
- **Satin:** follows a centerline with uniformly spaced samples and alternating constant-width rails. The width is physical millimeters; long crossings subdivide to the maximum stitch length. This is a centerline satin algorithm. It does not infer paired complex rails, stitch angles around difficult corners, or split-width satin automatically.
- **Fill:** alternates scanline direction at the chosen angle and maximum row spacing. It resolves compound fill rules, transformed geometry, nested clipping masks, and the physical decoration face. Each filled interval is separate needle work, connected by explicit travel; it does not sew across holes. This basic fill leaves travel between rows and disconnected islands. It does not optimize routing into a commercial tatami program. Intervals narrower than 0.24 mm are omitted to preserve curve/quantization clearance. Regions producing no stitches fail explicitly.

There is no image-to-stitch inference: trace images and separate gradient colors into explicit vector regions first. Effects must be removed. Running and satin follow explicit paths: already-contained paths may retain a source mask or face boundary, but a path that would leave it fails rather than being silently intersected or rerouted. Clipped fills are supported. Source masks are dependencies rather than independent embroidery. The default region builder uses explicitly assigned **Stitch** role layers when present, otherwise printable vector/text layers. Regions can subsequently select layers or groups directly.

All needle coordinates are integer tenths of a millimeter, positive Y down as in the artwork. The hoop origin is its center. Hoop width/height are 20–500 mm, margin is at least 0.5 mm, threads are bounded at 32, regions at 128, needle commands at 200,000, and stitches at 100,000 or the lower configured limit. Flattened geometry and scanline intersection work have independent caps. Preflight checks finite settings, references, thread changes, maximum stitch movement, program termination, physical face bounds, and usable hoop bounds. Running/satin containment samples sewn segments at 0.05 mm intervals under the same work cap. There is no automatic re-centering that changes the saved design's alignment. Opt-in physical thread diameter can increase clipping clearance; [schema-28 process settings](embroidery-process.md) describe underlay and locks.

## Native and MCP output

`form_update_object` accepts `embroidery` with `threads`, `regions`, hoop dimensions, margin, travel-trim threshold, and maximum stitch count. `null` removes those settings. A locked decoration rejects digitizing edits. Existing `form_export_artwork` now supports `format: "dst"`, `"json"`, or `"preflight"` for actual embroidery; `format: "svg", embroidery_format: "svg"` emits an actual-size needle-path SVG rather than ordinary artwork. `show_jumps: false` hides travel in that SVG while retaining it in program metadata.

The preflight response includes stitch/command counts, physical bounds, ordered thread passes, source digest, hoop dimensions, and explicit limitations. JSON retains the exact generated commands and settings. SVG uses a millimeter-sized hoop page, includes the same command program as metadata, and identifies stitches, jumps, trims, color changes, and end commands separately.

DST output has a 512-byte header, three-byte movement records, 0.1 mm coordinates, and ±12.1 mm per-axis record limits. Longer travel is divided into legal records. The first move is explicit travel from hoop center. Color changes and program end use their dedicated DST commands. A trim is the conventional three-jump sequence `(0.2,0.2),(-0.4,-0.4),(0.2,0.2)` mm, which returns to the same needle position. **DST has no dedicated trim opcode or embedded RGB thread palette.** Machine interpretation of jump-trim conventions varies. An adjacent `.threads.json` records the ordered thread passes and their colors/catalog details, hoop/bounds, and matching source digest. Both files are staged before replacing output; failed preflight leaves existing files intact.

Embroidery, manufacturing role artwork, sewing patterns, and fabric yardage are separate export choices; mixed selectors fail rather than silently choosing one. No embroidery export sends, queues, or starts a machine job.

## Limits and verification

These are real needle programs, not verified sew-outs. Underlay and backtracking tie-in/tie-off stitches are applied only when explicitly configured. No pull compensation, fabric/needle/tension simulation, short-stitch removal, or machine-specific safety tuning is inferred. Previewing a program and passing geometric preflight do not establish sewing quality. Production digitizer review and a physical sample remain necessary; machine integration is outside this implementation.

`EmbroideryTests` exercises all 59,049 legal DST axis pairs, independent known bit positions, physical running/satin/fill behavior, compound holes/inherited masks, curve geometry, thread changes, deterministic regeneration, bounded failures, physical SVG, and schema persistence. `EmbroideryEditingTests` exercises shared native/MCP settings and Undo, disk restart, physical exports and sidecars, rejection without replacing files, and actual-command native rendering with travel visibility and playback.

The validation-only independent reader is [EmbroidePy/pyembroidery](https://github.com/EmbroidePy/pyembroidery), pinned at 1.5.1 in an isolated `.local/validation/embroidery-reader-venv`. Run `scripts/verify_embroidery_dst.py` with its Python against DST, program JSON, and the thread sidecar. It independently decodes every expanded movement/control record, compares all needle coordinates, confirms trim interpretation preserves needle points, checks usable hoop bounds, and matches the sidecar's ordered colors and digest. `scripts/smoke_embroidery.py` runs the corresponding packaged MCP workflow in a guarded disposable `.local` library, including edits/regeneration, Undo, locked rollback, mixed-output rejection, exact source preservation, and reopen.

## Primary references

The method distinctions follow Ink/Stitch's [running stitch documentation](https://inkstitch.org/docs/stitches/running-stitch/) and [satin column documentation](https://inkstitch.org/docs/stitches/satin-column/); FORM's bounded implementations and limits above are its own. Ink/Stitch's [stitch library](https://inkstitch.org/docs/stitch-library/) documents the broader method families and reinforces the distinction between line work and fill.

DST bit fields, axis conventions, header structure, and the three-jump trim convention were researched against the official MIT-licensed [Pyembroidery DST writer](https://github.com/EmbroidePy/pyembroidery/blob/main/pyembroidery/DstWriter.py) and [DST reader](https://github.com/EmbroidePy/pyembroidery/blob/main/pyembroidery/DstReader.py). FORM's Swift encoder was independently implemented; the external reader supplies a separate decoding implementation for verification. These format references do not establish compatibility with every embroidery machine.
